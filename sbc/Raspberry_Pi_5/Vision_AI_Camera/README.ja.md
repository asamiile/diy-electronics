# 室内エリア別利用状況データ収集カメラ

[English](README.md) | [日本語](README.ja.md)

## 概要

室内の手前の作業スペース・奥のドアスペースを巡回して人物の有無を観測し、利用状況を分析・可視化できるデータをクラウドに蓄積するプロジェクトです。画像・動画は保存せず、観測結果の数値メタデータを保存します。

## 機能

- AIカメラ（Vision AI V2）での人物検知
- 単一エリアでの観測
- 複数サンプル判定（5回観測）
- JSON作成・ローカル保存
- API経由でBigQueryに送信

## 開発

### 仕様

#### MVP

- まず1エリア固定で人物検知・クラウド保存を確認し、最終的に登録した2エリアを雲台で巡回する。
- 雲台停止後に複数回観測し、人物あり・人物なし・判定不能を判定する。
- 1観測1レコードのJSONをPiから認証付きHTTPSで受信APIへ送り、BigQueryに蓄積する。
- 通信断中はPiに記録を一時保存し、復旧後に再送する。同じ `event_id` を再利用し、保存側で重複排除する。
- 期間・エリア別にSQLで取得でき、将来の可視化ツールから利用できる状態を完成条件とする。

ダッシュボードアプリの開発、個人識別、人物追跡、骨格・行動解析、音声認識、温湿度・照度測定はMVPに含めません。検知人数は観測方向内の人数であり、室内全体の人数や個人の滞在履歴ではありません。

#### 設置位置と観測エリア

縦長の部屋の手前の隅（下図の左下）にカメラを固定し、奥へ向けて観測します。手前を作業スペース、奥をドアスペースの2エリアに分けます。

```text
             奥
┌────────────────────┐
│       ドア         │
│                    │
│   ドアスペース     │
│    door_area       │
│                    │
│   作業スペース     │
│    work_area       │
│     机・椅子       │
│ カメラ ↗           │
└────────────────────┘
             手前
```

カメラは棚・壁など高さを確保できる場所に固定し、設置高さは着席した人物とドア前の人物の見え方を確認して決定します。作業方向では下向き、ドア方向では奥向きにパン・チルトを調整する案です。高さ・角度・有効距離は実機検証前であり、固定値として保証しません。

| エリアID    | 観測対象           | 観測方向・判定範囲                                            |
| ----------- | ------------------ | ------------------------------------------------------------- |
| `work_area` | 手前の机・椅子周辺 | 近距離の着席人物が映る方向。画面内の机・椅子周辺をROIに指定。 |
| `door_area` | 奥のドア前         | 奥向きの方向。画面内のドア前に人物が立つ範囲をROIに指定。     |

雲台は2方向を交互に巡回し、「移動 → 停止・待機 → 観測 → 判定・保存」を繰り返します。両エリアの同時観測は行いません。ドア側は短時間の通過を見逃す可能性があるため、利用傾向の観測に使い、漏れのない入退室件数として扱いません。

#### ROIによるエリア判定

各観測方向に矩形のROI（判定対象範囲）を設定し、信頼度閾値を満たす人物検知枠の中心がROI内（境界を含む）にある場合だけ、そのエリアの人物として数えます。サンプル数・人数・信頼度の集計にもROI内の検知だけを使います。ROI設定が未定義・不正の場合は `unknown` とし、`error_code` を `invalid_roi` にします。

ROI座標は検知枠と同じ画像座標系で、左上を原点に幅・高さを0〜1へ正規化した `x_min`・`y_min`・`x_max`・`y_max` を保存します。モデル入力のリサイズ・クロップ等がある場合は座標系を揃えてから判定します。ROI変更も `config_version` を更新し、クラウドの設定履歴に残します。

ROIは画面上の範囲であり、部屋の奥行きを測定するものではありません。手前の人物がドアのROIと重なる場合や、家具・人物で奥が隠れる場合は正しく分離できないため、設置高さ・観測方向・ROIを調整します。

#### 観測・判定

以下の値は初期案です。実機で調整し、変更時は設定バージョンを更新します。

| 項目         | 初期案                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| 巡回         | 2エリアを登録順に観測。各エリア約30秒間隔を目標とする。                                              |
| 停止後の待機 | 1秒。移動中は観測に使用しない。                                                                      |
| サンプル数   | 1観測につき5回。                                                                                     |
| 人物検知閾値 | モデルの信頼度0.7以上。                                                                              |
| 状態判定     | 正常5回中3回以上で人物検知なら `occupied`、それ以外は `empty`。正常サンプルが5回未満なら `unknown`。 |
| 時刻         | 観測開始時刻をミリ秒精度のUTCで保存。観測前に時刻同期を確認。                                        |
| 待機処理     | センサ・通信にタイムアウトを設け、待機で巡回処理が停止し続けない構成にする。                         |

`empty` は今回の観測で人物あり判定に至らなかったことを意味し、物理的な不在を保証しません。`person_count` は `occupied` の場合、人物検知した正常サンプルの人数の中央値（偶数個では小さい側）とします。`confidence` は、それらのサンプルで得た人物検知の最大信頼度です。

#### 蓄積するデータ

観測記録は集計前の状態で残し、推定利用時間などは必要時にSQLで算出します。以下は想定例で、実測データではありません。

| フィールド              | 型・意味                                               |
| ----------------------- | ------------------------------------------------------ |
| `event_id`              | STRING。一意の観測ID。再送でも変更しない。             |
| `device_id`             | STRING。装置ID。                                       |
| `observed_at`           | TIMESTAMP。観測開始時刻、UTC・ミリ秒精度。             |
| `zone_id`               | STRING。エリアID。                                     |
| `occupancy_status`      | STRING。`occupied` / `empty` / `unknown`。             |
| `person_count`          | INTEGER。観測の代表人数。`empty`は0、`unknown`はnull。 |
| `confidence`            | FLOAT。代表信頼度。`empty`・`unknown`はnull。          |
| `valid_sample_count`    | INTEGER。正常サンプル数。                              |
| `positive_sample_count` | INTEGER。閾値以上の人物を検知したサンプル数。          |
| `pan_deg` / `tilt_deg`  | FLOAT。雲台への指示角度。                              |
| `model_version`         | STRING。使用モデル・ラベル対応を識別するバージョン。   |
| `config_version`        | STRING。エリア・観測条件の設定バージョン。             |
| `schema_version`        | INTEGER。データ形式のバージョン。                      |
| `error_code`            | STRING / null。判定不能の理由。正常時はnull。          |

#### 分析時の扱い

- `observed_at` の日付でパーティション分割し、`device_id`・`zone_id` でクラスタリングするテーブル設計を予定する。
- 検知率は「人物あり観測数 ÷ 判定可能観測数」。`unknown` は分母に含めず、判定可能な記録がなければnullとする。
- 滞在時間は巡回観測からの推定値。隣接する正常観測の中間時刻を状態境界とし、観測間隔が設定目標の2倍を超える区間や判定不能区間は推定時間から除外する。
- Pi停止などでレコード自体がない期間は観測欠落として扱い、人物なしで補完しない。
- 観測時刻が異なるエリアの人数を合計して室内人数にしない。
- 観測記録90日、日別集計1年を保存期間の初期案とする。日別集計の生成・保存方式は実装時に決定する。
- 一時保存の容量上限と再送方針は実装時に決定し、容量不足を記録する。保存成功の応答後に送信済みへ変更する。

### ハードウェア開発

#### 配線

```text
OV5647-62 ──FFC──→ Vision AI V2 ──USB-C⇔USB-A──→ Raspberry Pi 5
                                                    │ GPIO（I2C）
                                                    ↓
                                    雲台制御基板（PCA9685）──→ サーボ×2
```

| 接続元         | 接続先         | 接続方式                     | 備考                                     |
| -------------- | -------------- | ---------------------------- | ---------------------------------------- |
| OV5647-62      | Vision AI V2   | FFCケーブル                  | ピン数・向きは実物で確認。               |
| Vision AI V2   | Raspberry Pi 5 | USBデータケーブル            | 結果取得方式は実装時に検証。             |
| Raspberry Pi 5 | 雲台制御基板   | 同梱ジャンパワイヤ4本（I2C） | SDA・SCL・VCC・GND。下表参照。           |
| 雲台制御基板   | サーボ×2       | サーボケーブル               | ケーブル色は基板のシルク表示に合わせる。 |

| Raspberry Pi 5 GPIO           | 雲台制御基板 |
| ----------------------------- | ------------ |
| 3番ピン（GPIO 2 / SDA）       | SDA          |
| 5番ピン（GPIO 3 / SCL）       | SCL          |
| 5V（2・4番）または3.3V（1番） | VCC          |
| GND（6番など）                | GND          |

B0283のマニュアルでは、制御基板をPiのGPIOにつなぐだけで、別電源は使いません。制御基板の動作電圧は3.3V/5V、サーボの定格は3.6〜4.8V・350mA未満です。VCCを5Vと3.3Vのどちらに接続するかは、基板のシルク表示とArducamのデモ手順で確認します。

サーボ動作時にPiが再起動・不安定になる場合は、手持ちの5V/4A ACアダプターで雲台を別給電します。その場合もPiと雲台のGNDは共通にします。サーボ定格の上限は4.8Vのため、5V給電で問題がないかを動作確認します。

### ソフトウェア開発

#### 構成と実装順序

```text
OV5647-62 → Vision AI V2 → Raspberry Pi 5
                            ├─ 雲台の巡回制御・観測判定
                            ├─ 未送信記録の一時保存
                            └─ HTTPS → 受信API → BigQuery
                                                  └─ 必要時にSQL・可視化ツールで利用
```

クラウドは受信APIとBigQueryを採用する計画です。APIの実行基盤、認証方式、テーブル名は実装時に確定します。PiのOS・Python・ライブラリのバージョン、モデルの対応と性能も未検証です。共通の認証・デプロイ手順は[認証情報管理](../../../docs/credentials.ja.md)と[Cloud Functionsガイド](../../../docs/cloud-functions.ja.md)を参照してください。

1. 1エリア固定で人物検知モデルとPiへの結果取得を確認する。
2. JSON作成、Piでの一時保存、API経由のBigQuery保存を実装する。
3. 雲台の制御を確認し、2エリア巡回と複数サンプルの判定を追加する。
4. 通信断・再起動・再送・重複排除を検証し、SQLで記録を取得する。

#### Raspberry Piのセットアップ

OSの書き込みと初期設定は[Raspberry Pi初期セットアップガイド](../../../docs/raspberry-pi-setup.ja.md)を参照してください。

`raspi-config` でI2Cを有効にし、雲台制御基板が認識されることを確認します。PCA9685の初期アドレスは `0x40` です。

```bash
i2cdetect -y 1
```

雲台の動作確認には、まずArducamのデモ（[ArduCAM/PCA9685](https://github.com/ArduCAM/PCA9685)）を使います。巡回制御はPythonで実装する予定で、PCA9685用ライブラリ（`adafruit-circuitpython-servokit` など）がPi 5で動作するかを検証します。
